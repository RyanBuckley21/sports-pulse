Design tokens — Phase 1 proposal

One consolidated token set for app.css + insights.css. Nothing here is wired into the live site yet — this page is standalone and links neither stylesheet, so it can be reviewed (and rejected) without touching a single component.

proposal only · no production CSS modified

1. Surfaces

Insights' three-level ramp wins over app.css's two. Its darks are also slightly lifted off pure black, which stops OLED crush and lets --surface read as a distinct layer.

--bg #0c0d10 insights.css

App background. Insights' value; app.css's #0A0A0B is near-black and clips on OLED.

--surface #16181d insights.css

Cards, rows, the resting panel level.

--surface-2 #1c1f26 insights.css

Lifted panels: expanded rows, pill cells, AI note. No equivalent in app.css.

5. The real collision isn't accent vs gold

Measured hue separation across the three warm tokens:

--accent 22°
--gold 36°
--warning 43°

--accent → --gold is 14°. But --gold → --warning is only 7°, at a 2% luminance difference.

Flagging, not fixing. --warning (#FBBF24) is closer to --gold than --gold is to --accent. Today that's survivable because they never co-occur — --warning only tints the staleness dot and its label in the header, while --gold lives in card bodies. But the moment a tab bar or persistent header puts a stale-data indicator on screen alongside a Signal Score, a user sees two golds meaning unrelated things. Cheapest fix is pushing --warning amber-ward toward ~55° and desaturating slightly, which reads more like "caution" anyway. I did not change it — it's a live semantic color and this phase is proposal-only.

But there is a real problem underneath. These hexes are injected inline and bypass the token system entirely, and 9 of 30 sit inside the warm band the accent tokens occupy — BAL, DET, HOU, MIL, NYM, PIT, SD, SF, WSH read as --accent; BAL, DET, HOU, MIL, NYM, PIT, SD, SF read as --gold. This is a Phase 3 problem, not a token-file problem — the fix is a rule about where team color is allowed to appear (identity slots like the abbr chip and rank bar) versus where only semantic tokens may appear (any score, any badge). Noting it now so Phase 3 doesn't rediscover it.

8. Type

Two findings first. --font-head is referenced in an insights.css comment but never actually declared — Bricolage is hardcoded in 12 font shorthands. Also, every Bricolage stack in insights.css ends at 'Space Grotesk' with no generic fallback — so when the Google Fonts request fails, headings drop to the browser's default serif rather than a sans. I hit exactly that rendering this page offline. The token file should define the stacks with system-ui, sans-serif terminators. And the two files disagree on face count: app.css uses JetBrains Mono in 19 places, while insights.css uses it zero times and its header comment explicitly says "No monospace, no serif."

Open question — 2 faces or 3? Consolidating means picking. Mono currently carries the staleness readout, rank numbers and the Insights back-link; dropping it means restyling those, keeping it means Insights' stated two-face rule is dead. I lean keep mono, scoped to numeric/system text only (timestamps, ranks) — it's doing real work distinguishing machine output from prose — but this is yours to call.
